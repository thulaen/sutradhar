# 0001: The door

The door is the wall in front of Forgejo's `main`. Every push to
Forgejo passes through it, even one made with the local hooks skipped.
It is roadmap Phase 1 items 3 and 4. The rules it enforces are in
[AGENTS.md sections 7 to 9](../../AGENTS.md#7-the-gate).

## What it does

1. Forgejo's pre-receive hook, `docker/forgejo/door-pre-receive.sh`,
   runs before Forgejo accepts a push. For each pushed ref, it packs the
   new objects and sends them, with the ref's name, its old and new
   commits and the current `main`, to the door over a local socket. It
   makes no decision itself.
2. The door, `aegis-door`, decides:
   - A delete, or any ref other than `main` and release tags (`v` and a
     version), is refused.
   - A release tag may only be new, and must name a commit on both the
     `main` the door accepted and Forgejo's `main` from before this push
     (the door can accept a `main` that Forgejo then turns down when
     another ref of the same push fails). So push `main` first, then its
     tag in a second push.
   - A push of `main` must keep its history: the last `main` the door
     accepted (`refs/door/main`) must be an ancestor of the new one. Only
     for the very first push, before the door has accepted anything, is
     Forgejo's old `main` used.
   - Before anything is written out, the door refuses a push of `main`
     that brings more than 500 commits (the very first push, made once at
     set-up, has no such limit), any file over 1 MiB in any of its
     commits, or whose newest tree holds more than 200,000 files or
     64 MiB in all, or is too big to list (`door.size`). The push tier
     also refuses a change of more than 32 MiB or a million lines, or one
     that names a file longer than 512 bytes. So a small pack cannot fill
     the disk or keep the door busy for hours.
   - The door unpacks the objects into its own copy of the repository,
     checks out the new commit, and runs the push tier on it. Before the
     checkout it writes `* -filter` to its copy's `info/attributes`,
     git's own override, so no filter a pushed `.gitattributes` names
     (such as git-lfs) runs on the door's computer.
3. Forgejo takes the push only if the door says yes for every ref.
4. When a push of `main` passes, the door points `refs/door/main` at it,
   so every accepted commit stays in the door's copy. That ref, not
   Forgejo's report, is the base for the next push: Forgejo's record of
   `main` could be lost or reset outside the door.

## Why it is built this way

- The door runs from a program built from code already accepted, not
  from the push, so a push cannot change the checks that judge it.
- Only the door's own account and Forgejo's may reach the socket.
- The door answers one push at a time, which suits work on one branch.
- A caller that goes quiet for 60 seconds is dropped. A slow check is
  never cut short.
- Cargo settings files in the tree are refused, since they could change
  how the checks run.

## Installing and updating

On Dell, from the repository's top folder, on the commit just accepted:

```
deploy/door/install.sh DOOR_DIR FORGEJO_UID
deploy/door/install-hook.sh DOCKER_COMMAND...
```

- `DOOR_DIR` is a private folder on Dell. It holds the program (`bin`),
  the socket (`run`) and the door's copy of the repository (`work`).
- `FORGEJO_UID` is the Dell user id that Forgejo's container runs as.
- The first script builds the door, installs it as the system service
  `sutradhar-door`, and writes `docker/forgejo/.env`, which is never
  committed. That file holds one line: `SUTRADHAR_DOOR_DIR=` and the
  socket folder.
- The second script restarts Forgejo with that folder mounted at
  `/door`, and puts the hook in place.

Run both again after any accepted change to `crates/aegis`,
`crates/aegis-door` or the hook.

## Settings

The gate and the door read these settings:

- `AEGIS_QUEUE` names pankti, the heavy-job queue. When it is set, the
  Rust checks wait in the queue and run sealed.
- `AEGIS_PRIVATE` names the folder of the owner's private lists. The
  check `secrets.private-lists` reads them; with no folder named, as on
  a contributor's own computer, that check has nothing to read.
- `AEGIS_GRYPE_DB` names the folder where the image scanner keeps its
  list of known holes (check `images.holes`). It must be set, and must
  lie outside the repository, where no pushed code can write. The door
  and the push hook take it from the setting `sutradhar.grypedb`.
- `GIT_INDEX_FILE` is git's own. When a hook gives one, the commit tier
  checks that index, not the usual one.
- `DOOR_SOCKET` tells Forgejo's hook where the door listens; it is
  `/door/door.sock` when unset.

## How it is tested

- `crates/aegis-door/tests/rules.rs` and `tests/socket.rs` run the door
  on scratch repositories: good pushes, first pushes, bad messages,
  rewritten history, a lost `main`, deletes, other refs, tags (including
  a door that has accepted nothing), pushes too big to write out, broken
  requests and the real program on a socket.
- A push made with `--no-verify` that breaks a check is refused by
  Forgejo.
