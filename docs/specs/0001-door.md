# 0001: The door

The door is the wall in front of Forgejo's `main`. Every push to
Forgejo passes through it, even one made with the local hooks skipped.
It is roadmap Phase 1 items 3 and 4. The rules it enforces are in
[AGENTS.md sections 7 to 9](../../AGENTS.md#7-the-gate).

The separate trusted [load-test gate](0134-ci-latency-load-gate.md)
uses signed, tier-bound receipts from the door under DR-121.

## What it does

1. Forgejo's pre-receive hook, `docker/forgejo/door-pre-receive.sh`,
   runs before Forgejo accepts a push. For each pushed ref, it packs the
   new objects and sends them, with the ref's name, its old and new
   commits and the current `main`, to the door over a local socket. It
   makes no decision itself.
2. The door, `aegis-door`, decides:
   - A delete, or any ref other than `main` and release tags (`v` and a
     version), is refused.
   - A release tag may only be new, and must name a commit on both the
     `main` the door accepted and Forgejo's `main` from before this push
     (the door can accept a `main` that Forgejo then turns down when
     another ref of the same push fails). So push `main` first, then its
     tag in a second push.
   - A push of `main` must keep its history: the last `main` the door
     accepted (`refs/door/main`) must be an ancestor of the new one. Only
     for the very first push, before the door has accepted anything, is
     Forgejo's old `main` used.
   - Before checking out or accepting the candidate `main`, enforce
     the commit limit in AGENTS.md section 8.5 (ADR-0021, Delivery).
     Count all commits reachable from the proposed tip and absent from
     the accepted base above. If there is no base, count the whole
     candidate history. Refuse a missing or invalid count, or an excess
     without a valid signed owner waiver (`door.size`).
   - The door also refuses any file over 1 MiB in any of its
     commits, or a newest tree that holds more than 200,000 files or
     64 MiB in all, or is too big to list (`door.size`). The push tier
     also refuses a change of more than 32 MiB or a million lines, or one
     that names a file longer than 512 bytes. So a small pack cannot fill
     the disk or keep the door busy for hours.
   - The door unpacks the objects into its own copy of the repository,
     checks out the new commit, and runs the push tier on it. Before the
     checkout it writes `* -filter` to its copy's `info/attributes`,
     git's own override, so no filter a pushed `.gitattributes` names
     (such as git-lfs) runs on the door's computer.
3. Forgejo takes the push only if the door says yes for every ref.
4. When a push of `main` passes, the door points `refs/door/main` at it,
   so every accepted commit stays in the door's copy. That ref, not
   Forgejo's report, is the base for the next push: Forgejo's record of
   `main` could be lost or reset outside the door.

### Exact push evidence

`REQ-0001-PUSH-IDENTITY`, `DES-0001-PUSH-IDENTITY` and
`VAR-0001-PUSH-SAME-TREE` bind the one-ref `main` acceptance path to
`TASK-0001-DOOR-GATE`. See the

The door checks the exact proposed commit under the accepted base from
item 2. Bind repository, ref, the exact accepted base and proposed
commit identities and their tree identities to the applicable check
profile. Equal trees do not make different commits interchangeable.
Refuse mismatched, missing or stale required evidence before accepting
the ref. Use [spec 0003](0003-toolchain-and-check-runner.md#results) for
signed evidence admission. Keep the configured bootstrap profile and
the existing signature and waiver rules.

In the planned `BDD-0001-DOOR-WRONG-COMMIT` fixture, present evidence
from another commit with the same tree and base. The mismatch leaves
both the door's accepted ref and Forgejo's ref unchanged. The exact
eligible push advances both once. The existing wrong-tree case also
traces to this requirement. Neither result serves as a commit-tier,
phase exit or release verdict.

## Why it is built this way

- The door runs from a program built from code already accepted, not
  from the push, so a push cannot change the checks that judge it.
- Only the door's own account and Forgejo's may reach the socket.
- The door answers one push at a time, which suits work on one branch.
- A caller that goes quiet for 60 seconds is dropped. A slow check is
  never cut short.
- Cargo settings files in the tree are refused, since they could change
  how the checks run.

## Installing and updating

On Dell, from the repository's top folder, on the commit just accepted:

```
deploy/door/install.sh DOOR_DIR FORGEJO_UID
deploy/door/install-hook.sh DOCKER_COMMAND...
```

- `DOOR_DIR` is a private folder on Dell. The bootstrap installer
  uses `bin` for the door program, `run` for its socket and `work`
  for its copy of the repository.
- Under [0007](0007-performance-and-engineering-gates.md#forced-speed),
  the door owns its timing evidence and alone writes the `speed`
  store in `DOOR_DIR` (AGENTS.md sections 6 and 11). The speed
  provisioning contract permits an empty initial store only when
  there is no existing store and the door has recorded no time.
  Preserve any existing store. A missing or unreadable store makes
  the door refuse to record or accept times under 0007.
- `FORGEJO_UID` is the Dell user id that Forgejo's container runs as.
- The first script builds the door, installs it as the system service
  `sutradhar-door`, and writes `docker/forgejo/.env`, which is never
  committed. That file holds one line: `SUTRADHAR_DOOR_DIR=` and the
  socket folder. The bootstrap service uses the invoking user and
  group. Shared-account sessions permitted by AGENTS.md section 11
  remain unmanaged. Protected installations follow
  [0008](0008-trust-boundaries.md#protected-policy-and-installed-tools).
- The second script restarts Forgejo with that folder mounted at
  `/door`, and puts the hook in place.

Run both again after any accepted change to `crates/aegis`,
`crates/aegis-door` or the hook.

### Load-gate evidence

The door owns the private load-gate namespace for 0134. It admits
and records accepted evidence through the protected store route.
The owner policy signs workloads. The sealed runner signs baselines
and run receipts, and independent reviewers own p99 review evidence
under 0134. The door and 0005 read verified exact-scope records through
that route. A candidate or public report cannot write accepted evidence.
Keep the load namespace separate from the 0007 `speed` store. A missing,
unreadable or unadmitted load store leaves the affected load result
unverified. Preserve prior verified records and their original scope.

Admit the exact protected evidence profile under 0008 and 0065 before
using the namespace. The door and protected runner evidence owners
must provide the verified store identity, authorised writers and
readers, approved record encoding and signing purposes, currentness
rules, byte and retention bounds, and cleanup and recovery proof.
For release use, verify those inputs under QR-101. A profile that keeps
raw vectors after sealing must also prove its separate admitted custody
and cleanup. Without the applicable proof, hold use of that profile.
The Phase 2 synthetic LOAD-0134-DOOR case tests receipt checking only.

## Settings

The gate, the door and the local git hooks read these settings:

- `AEGIS_QUEUE` names pankti, the heavy-job queue. When it is set, the
  Rust checks wait in the queue and run sealed.
- `AEGIS_PRIVATE` names the folder of the owner's private lists. The
  check `secrets.private-lists` reads them; with no folder named, as on
  a contributor's own computer, that check has nothing to read.
- `AEGIS_GRYPE_DB` names the folder where the image scanner keeps its
  list of known holes (check `images.holes`). It must be set, and must
  lie outside the repository, where no pushed code can write. The door
  and the push hook take it from the setting `sutradhar.grypedb`.
- `SUTRADHAR_AGENT` names the agent in the mailbox for the local commit
  and push hooks. When the checkout's setting `sutradhar.mailbox` names
  the mailbox's folder, the hooks refuse a commit or push that takes a
  file under a live lock, and refuse to run without this name (AGENTS.md
  section 8.2).
- `GIT_INDEX_FILE` is git's own. When a hook gives one, the commit tier
  checks that index, not the usual one.
- `DOOR_SOCKET` tells Forgejo's hook where the door listens; it is
  `/door/door.sock` when unset.

## How it is tested

- Exercise the governing commit limit at the limit and one above.
  Count the exact ref range once, including newly reachable merge
  ancestry. Test the first push with an existing Forgejo base and
  with no base. Test missing counts, tampered or stale waivers and
  a waiver scoped to the exact change. A refused push leaves the
  accepted ref untouched.

- `crates/aegis-door/tests/rules.rs` and `tests/socket.rs` run the door
  on scratch repositories: good pushes, first pushes, bad messages,
  rewritten history, a lost `main`, deletes, other refs, tags (including
  a door that has accepted nothing), pushes too big to write out, broken
  requests and the real program on a socket.
- A push made with `--no-verify` that breaks a check is refused by
  Forgejo.
