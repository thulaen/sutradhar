# 0001: The door

The door is the wall in front of Forgejo's `main`. Every push to
Forgejo passes through it, even one made with the local hooks skipped.
It is roadmap Phase 1 items 3 and 4. The rules it enforces are in
[AGENTS.md sections 7 to 9](../../AGENTS.md#7-the-gate).

## What it does

1. Forgejo's pre-receive hook, `docker/forgejo/door-pre-receive.sh`,
   runs before Forgejo accepts a push. For each pushed ref, it packs the
   new objects and sends them, with the ref's name, its old and new
   commits and the current `main`, to the door over a local socket. It
   makes no decision itself.
2. The door, `aegis-door`, decides:
   - A delete, or any ref other than `main` and release tags (`v` and a
     version), is refused.
   - A release tag may only be new, and must name a commit on `main`.
   - A push of `main` must keep its history: the old `main` must be an
     ancestor of the new one.
   - The door unpacks the objects into its own copy of the repository,
     checks out the new commit, and runs the push tier on it.
3. Forgejo takes the push only if the door says yes for every ref.
4. When a push of `main` passes, the door points `refs/door/main` at it,
   so every accepted commit stays in the door's copy.

## Why it is built this way

- The door runs from a program built from code already accepted, not
  from the push, so a push cannot change the checks that judge it.
- Only the door's own account and Forgejo's may reach the socket.
- The door answers one push at a time, which suits work on one branch.
- A caller that goes quiet for 60 seconds is dropped. A slow check is
  never cut short.
- Cargo settings files in the tree are refused, since they could change
  how the checks run.

## Installing and updating

On Dell, from the repository's top folder, on the commit just accepted:

```
deploy/door/install.sh DOOR_DIR FORGEJO_UID
deploy/door/install-hook.sh DOCKER_COMMAND...
```

- `DOOR_DIR` is a private folder on Dell. It holds the program (`bin`),
  the socket (`run`) and the door's copy of the repository (`work`).
- `FORGEJO_UID` is the Dell user id that Forgejo's container runs as.
- The first script builds the door, installs it as the system service
  `sutradhar-door`, and writes `docker/forgejo/.env`, which is never
  committed. That file holds one line: `SUTRADHAR_DOOR_DIR=` and the
  socket folder.
- The second script restarts Forgejo with that folder mounted at
  `/door`, and puts the hook in place.

Run both again after any accepted change to `crates/aegis`,
`crates/aegis-door` or the hook.

## How it is tested

- `crates/aegis-door/tests/rules.rs` and `tests/socket.rs` run the door
  on scratch repositories: good pushes, first pushes, bad messages,
  rewritten history, deletes, other refs, tags, broken requests and the
  real program on a socket.
- A push made with `--no-verify` that breaks a check is refused by
  Forgejo.
