# 0037: Third-party extension isolation

An extension is extra analysis written by someone else, such as a spam
scorer from another developer. Sutradhar runs each one sealed off in
its own locked room, built from Linux's own controls (namespaces,
seccomp, Landlock and control groups), with no Docker or other
container program on the owner's PC: it gets only the
data it asked for and the administrator agreed to, a fixed amount of
memory and processor time, and no way to touch the site, the database
or other extensions. What it produces are proposals that staff review
like any other suggestion. If it crashes or misbehaves, only that
extension stops. It is roadmap Phase 5 item 5, beside the `sutra`
command and the MCP server.

Example: an administrator adds "Thread quality scorer 1.2". The Add
screen shows that it wants to read guest-visible posts and propose
moderation hints, uses 256 MiB, has not been reviewed by the project
and has no internet access. The administrator ticks "I understand" and
approves. Next day it runs out of memory; only its sandbox stops, the
Extensions screen shows "Stopped: used more than its 256 MiB
(SUT-813)", and suggestions continue.

## What it does

### Terms

- Extension: a third-party package of analysis code: one archive
  pinned by its SHA-256 digest (a fingerprint of the exact bytes),
  holding a self-contained Linux x86-64 program, its read-only data
  files and a manifest file. The program may be written in any
  language; it needs nothing installed on the owner's PC.
- Sandbox: the sealed room an extension runs in, made by Sutradhar
  from Linux's own controls. No container program is used or needed on
  the owner's PC.
- Manifest: `sutradhar-extension.toml`, declaring what the extension is,
  what it may do and what it may use.
- Grant: one permission from a fixed list, such as "read guest-visible
  posts".
- Broker: the Rust service extensions talk to; their only door.
- Allowance: the memory, processor, disk and request rate an extension
  declares and the administrator approves.

### Scope

In scope: the manifest and its checks; the review tier and the warning
for unreviewed packages; the broker and its grants; starting, stopping
and removing extension sandboxes through the host helper; fault
isolation; the Extensions screens and `sutra extension` commands; the
developer contract and a sample extension.

Out of scope: first-party modules, which are crates; community models
(spec 0024), which an extension gets only through that spec's checks;
and WebAssembly plug-ins, which are never offered (Q-EX03, which the
owner accepted on 31 October 2026 with "Accept all (Recommended)").

### Design

- `mandali::extensions` (in `sutradhar-mandali`, the modules crate):
  the manifest parser (serde, toml, garde), the registry of installed
  extensions and their lifecycle.
- `mandali::broker`: an Axum service reached only by extensions. Every
  request is signed with a per-extension key (`hmac` and `sha2`),
  checked against the extension's grants, rate-limited (`governor`) and
  logged.
- `sutradhar-host` (spec 0030): the only part allowed to start
  sandboxes. It accepts a generated sandbox description and refuses
  anything outside a strict allow list.
- `sutradhar-extension-sdk`: a small Rust crate for extension authors,
  with typed broker calls; the broker's OpenAPI document serves other
  authors.
- `namaste`: the sample extension used by the tests and the developer
  guide.
- Traits, each with a fake in development-only `sutradhar-test-support`
  (spec 0014): `SandboxRuntime`
  (`start`, `stop` with a grace period, `remove`, `stats`),
  `PackageVerifier` (`verify` a package to its digest) and `GrantPolicy`
  (`allows(extension, call) -> bool`).
- The manifest checker, runtime, policy and broker are separate parts.
  The broker depends on `GrantPolicy`, not on how grants are stored.
  One allow-list table serves both the description generator and the
  host helper's check. A fixed list of grants, not a policy language.

### The manifest

```toml
id = "example.quality-scorer"
name = "Thread quality scorer"
version = "1.2.0"
publisher = "Example Labs"
licence = "MIT"
package = "https://example.org/scorer-1.2.0.tar"
package_sha256 = "..."
contract = ">=1.0, <2.0"
grants = ["read.guest_posts", "propose.moderation_hints"]
[allowance]
memory_mib = 256
cpus = 0.5
disk_mib = 512
requests_per_second = 20
```

- The fixed grants: `read.guest_posts`, `read.threads`,
  `read.link_graph`, `propose.suggestions`, `propose.moderation_hints`,
  `write.own_store`, `emit.metrics`, `load.model` (data-only model
  formats only) and `network.internet`.
- Nothing grants writes to the site, Sutradhar's tables, settings or
  other extensions.
- Unknown keys or grants, missing limits, a missing or malformed digest,
  or a broker contract range outside what the broker offers refuse the
  manifest (SUT-810), each problem named.

### The sandbox

Generated by `mandali::extensions` and checked again by the host
helper, which builds it from Linux's own controls:

- its own user, mount, process, network and IPC namespaces, mapped to
  an unprivileged user with no rights outside;
- a read-only root holding only the package's files, with a small
  temporary area in memory; no other host folder and no socket but the
  broker's;
- every Linux capability dropped; no-new-privileges; a seccomp filter
  that allows only a reviewed list of system calls;
- Landlock rules: read only its package folder; write only its
  temporary area and, when `write.own_store` is granted, its own store
  folder of fixed size;
- its own control group inside the service slice: memory limit equal
  to memory-plus-swap limit (no swap); processor and process limits; a
  small init that reaps child processes;
- no network: the broker is reached over one Unix socket passed in at
  start. `network.internet` lets it ask the broker to make outbound
  HTTPS requests for it, each logged;
- restart on failure at most 3 times in 10 minutes, then quarantine.

### Lifecycle

1. Add: the administrator gives a manifest and package (screen or `sutra
   extension add`). Sutradhar downloads the package, or reads a given file,
   checks its digest, checks the manifest and that the allowance fits, and shows
   the review tier. `sutra extension check` runs the same checks offline.
2. Review tier: "Reviewed" (documented origin, compatibility tests and
   a security review recorded by the project) or "Not reviewed". For
   "Not reviewed", the screen shows every grant in plain English, the
   risks and the allowance; the administrator must tick and approve.
   Unreviewed extensions are approved by the owner and the
   administrators the owner permits. Approval is per site and audited.
3. Start: the host helper starts the sandbox; the broker waits for its
   health answer within 30 seconds.
4. Run: the extension reads through the broker and posts proposals,
   which enter the normal review queues with an "extension" badge. They
   become changes only through a moderator's approval.
5. Fault: isolate and report. Its results are withheld and its settings
   kept; the screen and staff alerts say why, with reasons on the
   detail screen.
6. Disable keeps everything. Remove stops it, deletes its sandbox,
   package and control group, and offers to export its own store before
   deleting it. Its audit entries stay.
7. Update: the store is exported first; steps are checkpointed. An
   upgrade is held, not forced, when an enabled extension's contract
   range excludes the new broker. A new version with new grants needs a
   fresh approval.
8. Withdrawn approval is refused at the extension's next call (SUT-814).
9. Background extension work yields to live work: when memory or
   processor is short, the broker answers extensions "wait" before live
   suggestions slow down.

### Data

In PostgreSQL, every table with row-level security on and forced. The
broker's role reads only the grants of the extension whose key signed
the request. Extensions never get a database role.

- `extensions`: id, version, manifest JSON, package digest, tier, grants
  approved, allowance approved, approved by, approved at, and state
  (added, running, disabled, quarantined, removed).
- `extension_keys`: id and key hash; the key itself only in the
  extension's sandbox, passed in at start.
- `extension_events`: id, time, kind (start, stop, crash, limit,
  refusal), detail code. Kept 90 days.
- Proposals reuse their feature's records with `source_extension`.

### API and events

- Admin actions, through the action layer: `mandali.extension.add`,
  `.approve`, `.start`, `.disable`, `.remove`, `.list`, `.describe`.
- Broker (the extension's own socket only): `GET /ext/v1/posts?since=`,
  `GET /ext/v1/threads/{id}`, `GET /ext/v1/links`, `POST /ext/v1/proposals`,
  `PUT /ext/v1/store/{key}`, `GET /ext/v1/health-check`. Each refused
  unless granted.
- Events: `extension.started`, `.stopped`, `.quarantined`, `.limit_hit`,
  `.refused_call`.

### Failures

- SUT-810 manifest invalid, each problem named.
- SUT-811 package digest does not match or cannot be fetched.
- SUT-812 allowance does not fit the extension pool.
- SUT-813 stopped for using more than its memory allowance.
- SUT-814 call refused: not granted.
- SUT-815 quarantined after 3 crashes in 10 minutes.
- SUT-816 health answer missing at start.
- SUT-817 over its disk allowance; stopped until cleared.
- SUT-818 rate limit reached.
- SUT-819 host helper unavailable.

New codes for the update and contract checks take numbers from the
central list. A crash, limit or refusal affects only that extension.
Proposals in flight when it stops are discarded unless the broker
already stored them. The broker never blocks the engine: each call has
a timeout and its own small pool.

### Security and privacy

- Extensions never hold database credentials, site keys or other
  extensions' keys. They see only guest-visible data, the same as any
  guest reads, treated as data.
- Every call is signed, with a 60-second window and a single-use number,
  checked against grants and logged by id.
- `network.internet` is shown with a red warning: the extension could
  send what it reads elsewhere.
- An extension cannot raise its own grants.
- The manifest's licence is shown; a missing licence gives a stronger
  warning.
- The extension SDK and the broker's contract are also offered under a
  permissive licence, besides AGPL-3.0-or-later.

### Screens

The Extensions list, Add, Review and Detail screens meet WCAG 2.2 AA:
the grant list is a real list, each grant a sentence; the "Not
reviewed" warning uses the SDS warning component with an icon and words,
never colour alone; the approval tick box has a visible label, and the
approve button stays disabled, with a reason in text, until ticked;
usage bars have text ("180 of 256 MiB").

### Capabilities

- Extensions list, Add, Review, `sutra extension add|approve`: CAP-019,
  "Add a third-party extension that runs isolated within limits".
- `sutra extension start|disable`: CAP-016, "Turn optional modules on or
  off".
- Fault display and quarantine reasons: CAP-017, "See which methods are
  waiting, isolated or faulty, and why".
- Developer contract, SDK and `namaste`: CAP-020, "Build a new module
  against the documented core contracts".
- `sutra extension remove`: NEW-032-A, "Remove an extension, keeping or
  deleting its own data".
- What an extension itself offers is the third party's and does not
  count as Sutradhar's.

### Edge cases

- The same package under two ids is refused: one digest, one extension.
- A package withdrawn by its publisher after approval keeps running
  from the local copy; re-adding needs the package again.
- A clock jump: signatures use the 60-second window and the single-use
  number.
- A broker restart: extensions retry with back-off; nothing they posted
  is lost once acknowledged.
- A model asked for goes through spec 0024's checks, and its memory
  counts in the extension's allowance.
- Uninstalling Sutradhar removes every extension first.

### Observability

`sutradhar_extension_memory_bytes{extension}`,
`_cpu_seconds_total{extension}`,
`_calls_total{extension,route,outcome}`,
`_restarts_total{extension}` and `_status{extension,status}`. Alerts:
quarantine, limit hits twice in a day, refusal spikes. One health row
per extension; staff alerts grouped by extension.

### Facts checked before building

That Ubuntu 26.04 lets the service make unprivileged user namespaces
(Ubuntu limits this through AppArmor, so the `.deb` may need to ship a
profile for the host helper); the Landlock version its kernel offers;
memory limits in a child control group of the service slice under
cgroup v2; disk limits for the own store (a fixed-size area, else size
checked periodically and the extension stopped); the reviewed seccomp
list; that a sandbox with its own network namespace has no route out;
and a licence review of whether an extension using only the broker's
contract is a separate work from Sutradhar.

## Limits

- Extension memory is inside the service slice, within the memory limits in
  AGENTS.md section 5.6, in an "extension pool" setting that starts at 0 MiB. An
  extension is added only if its allowance fits the pool. The pool grows only by
  lowering another part's budget or by measured headroom. The installer and the
  broker both refuse a total over the cap (SUT-812).
- The broker itself takes about 16 MiB (estimate) of the service's
  budget in the service slice.
- The published resource figures list every extension's allowance.
- Per extension: its declared memory, processor, disk and request rate;
  3 restarts in 10 minutes; 30 seconds to become healthy.
- Speed targets on Dell: a broker call, excluding returned data, p95
  under 5 ms; start to healthy under 30 s; a crash or limit shown within
  10 s; the Add screen's checks, excluding the download, under 3 s; with
  an extension at its processor limit, first-suggestion time for new
  posts changes by no more than 5%, and the 30-second level still holds.

This part adds nothing to public pages. Extensions only produce

## How it is tested

Rust tests unless named:

- EX-01: the `namaste` manifest is accepted, its grants listed in plain
  English, and nothing runs before approval.
- EX-02 (property): generated manifests with unknown keys, unknown
  grants, missing limits or a tag instead of a digest are refused with
  SUT-810 naming the problem.
- EX-03 (Dioxus app test): a "Not reviewed" package needs the tick, and
  approval is audited with the grants shown.
- EX-04 (unit and property): every generated description has its own
  namespaces, no host folder, no socket but the broker's, no added
  capability, a read-only root, the seccomp list, Landlock rules,
  equal memory and swap limits and no network; the host helper refuses
  a tampered one.
- EX-18 (Dell, a real kernel): a test package trying to open a host
  file, make a raw socket, call a refused system call or reach the
  internet without the grant is stopped by the sandbox, and no
  container program is present or used.
- EX-05: an extension with only `read.guest_posts` calling the proposals
  route gets SUT-814, and the refusal is logged.
- EX-06: with private sections on the site, only guest-visible posts are
  returned.
- EX-07 (chaos): `namaste` built to allocate past its allowance stops
  alone, SUT-813 shows and suggestions continue.
- EX-08: an extension crashing on start is quarantined after 3 restarts
  in 10 minutes with SUT-815 and one grouped staff alert.
- EX-09 (load): with an extension at its processor limit,
  first-suggestion time changes by at most 5%.
- EX-10: with a 256 MiB pool and 200 used, a 128 MiB extension is
  refused with SUT-812.
- EX-11: a proposal appears in the review queue with its badge and
  becomes a change only through a moderator's approval.
- EX-12: version 1.3 asking for `network.internet` does not run until
  approved again.
- EX-13: removal offers export, then the sandbox, package, control
  group and own store are gone and audit entries stay.
- EX-14 (unit and property): a wrong, old or replayed signature is
  refused.
- EX-15: every screen and state passes the accessibility checker, and
  screenshots match in both themes and widths.
- EX-16: Kani proofs hold and cargo-mutants leaves no surviving mutant
  for the allow list, `GrantPolicy`, signing and the budget check, for
  example "no generated description passes the allow list with a host
  folder, an extra socket or an added capability" and "approved allowances
  never add up to more than the pool".
- EX-17 (chaos): an extension trying to reach PostgreSQL or the site's
  database finds no route and no credential.
- Tests also cover the contract range, a held upgrade, per-site
  approval, refusal after withdrawal and export before update.
- Coverage is 100% of lines and branches; speed targets are held by the
  5% median rule of AGENTS.md 6.8.

## Changes from the source

- Screens are the Dioxus app built from SDS components, with Rust
  screen tests.
- Speed: the 5% median rule of AGENTS.md 6.8 replaces the old ratchet.
- Extensions run on the owner's PC, where the service runs, sealed off
  with Linux's own controls instead of containers, so the owner's PC
  never needs Docker; packages are pinned archives instead of container
  images. Their memory counts within the limits of AGENTS.md section
  5.6, not the old 5.6 GB.
- Mutation runs use cargo-mutants directly, built with Cargo.
